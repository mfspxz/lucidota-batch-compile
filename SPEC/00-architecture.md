# SPEC §12-1 — Architecture + Data Flow (re-scoped: minimal 7-stage loop)

**Mission 2 §1, §2, §8 synthesis agent, per OWNER DIRECTIVE — ARCHITECTURE SIMPLIFICATION.**
This file was re-scoped from the 7-stage-loop design; the earlier validator-hierarchy
rendering is superseded. Specification only — no code changes, no deletions, no deploys.

**The system is one loop:**
Prompts → Typed work order → Partitioner → Allocator → Workers → Ledger → fixed retry rules → repeat.

**What was CUT (owner directive):** any semantic-judge LLM, hierarchy of validators,
LLM-debates-LLM layers, autonomous reinterpretation of the human's objective.
A bad objective faithfully executed is a human/work-order problem, not a reason to build an
artificial judge.

**What stays, as deterministic operations (never judgment):**
- schema/hash/limit/test checks = **Compare / Calculate**
- authorization boundaries (governor / CANON gates) = **Compare against policy**
- quota accounting = **Calculate**
- routing / tracking / stopping = **Route / Track / Stop**

Structural integrity stays cheap and deterministic. Semantic judgment stays with the human
and the authoring LLM. (f1 INV-01: AI assertions cannot create PL VERIFIED — including
assertions *about* artifacts; only deterministic checks and authorized evidence do.)

**Authority frame (f1, EXISTING AND VERIFIED):** CANON > PL > GIT > AI. This document is
AI-tier: a proposal, not self-certifying. Anything marked UNKNOWN stays UNKNOWN.

## 1. The 7-stage loop

Mermaid:

```mermaid
flowchart TD
    PROMPTS[Prompts\nreusable instructions: authoring work orders,\nexecuting units, retry phrasing] --> WO[Typed work order\nwork + units + relationships + outputs\n+ resource limits — immutable once authored]
    WO -->|CANON/scope/policy Compare| GATE[authorization gate\nCANON normative basis + dispatch-gate\nadmit_action — Compare against policy]
    GATE -->|DENY| DENYLOG[deny receipt → Ledger]
    GATE -->|ALLOW + PL claim receipt| PART[Partitioner\ntyped units by EXPLICIT rules\ndev-graph enables edges]
    PART --> READY[readiness\ndevgraph cmd_ready:\nopen units with all enables-predecessors done]
    READY --> ALLOC[Allocator\neligible units → LLM sources under\nACTUAL capacity/rate limits]
    ALLOC -->|govern() + route() + quota reserve\nRoute| WORK[Workers\nbounded generation STRICTLY within assignment\nliteboxd prepare→start→inspect]
    WORK --> LEDG[Ledger\ninputs, allocations, outputs, attempts, results\nenvelope-claimed at dispatch, established at\ndeterministic acceptance]
    LEDG --> CHECK{deterministic check ops\nCompare / Calculate / Compare-against-policy}
    CHECK -->|pass| ACC[accepted — enables successors become ready]
    CHECK -->|fail, fixed rules| RETRY[fixed retry rules\n→ repeat: Allocator re-queues at tail]
    CHECK -->|fail, terminal| DL[dead-letter — Ledger records, loop continues]
    RETRY --> ALLOC
    ACC --> READY
```

Everything not in this loop was cut. The "validators" in the evidence bundle are
re-homed below as deterministic check ops — they do not form a hierarchy of judges.

## 2A. The 3-tier worker structure (inside the Workers stage)

Tiers are defined by **context/responsibility scope, NOT by model capability**.
N=3, fixed. Numbering is INVERTED from the original Mission 2 prompt: **Tier 1 is the top**.
All three tiers follow the same basic development rules with progressively broader context
and responsibility. No fourth tier.

```
┌─────────────────────────────────────────────────────────────────┐
│ Tier 3 — single-check workers                                   │
│  basic dev rules + ONE explicit checklist item + the specific   │
│  inputs/context for that check + defined output and completion   │
│  condition. Maximize independent parallel work, minimal context  │
│  overhead.                                                      │
│  Completion condition: the single check's defined output exists │
│  and its completion condition holds (per its prompt).           │
└──────────────────────────────┬──────────────────────────────────┘
                               │ Tier 3 results → shared context
┌──────────────────────────────▼──────────────────────────────────┐
│ Tier 2 — check-group workers                                    │
│  basic dev rules + a GROUP of related checklist items + the     │
│  relevant Tier 3 results and shared context + defined group-     │
│  level output and completion condition. Combines related        │
│  results, handles local dependencies, resolves bounded          │
│  inconsistencies within the group.                              │
│  Completion condition: group-level output exists; every item in │
│  the group resolved or explicitly carried as an open item; no   │
│  cross-group concern raised without being recorded.             │
└──────────────────────────────┬──────────────────────────────────┘
                               │ Tier 2 results + evidence
┌──────────────────────────────▼──────────────────────────────────┐
│ Tier 1 — full-context developer                                 │
│  complete dev rules + entire checklist + work-order objective +  │
│  relevant specs/architecture/constraints + Tier 2 results and   │
│  their evidence. Owns overall coherence and final integration;  │
│  addresses cross-group concerns.                                │
│  Completion condition: whole checklist accounted for;           │
│  cross-group concerns resolved; final integration output exists │
│  with all evidence bound.                                       │
└─────────────────────────────────────────────────────────────────┘
```

**Partitioning rule (structural, not judgment)** — encoded as a rule on the work graph:
a checklist item may go to Tier 3 **ONLY** if it is performable with its supplied context
alone (no `enables`-predecessor outside its own context, no dependency on another check's
output). Related or dependent checks stay grouped at Tier 2. This is a graph property
(checkable by `devgraph.py`: the item's `enables`-predecessors must all be satisfied by
the supplied context, not by sibling checks) — never a semantic judgment.

**Prompts:** developer-defined and developer-supplied. The scheduler distributes prompts
to tiers; it never authors, modifies, or judges them. A Tier 3 prompt that smuggles
judgment beyond its single check is a work-order defect (human/authoring-LLM problem),
not something the scheduler detects.

## 2B. The scheduler's deterministic op vocabulary

The scheduler (Allocator + Partitioner composer) speaks exactly six ops —
Partition / Group / Assign / Schedule / Record / Repeat — all deterministic:

| Op | Input → output | Op class |
|---|---|---|
| **Partition** | checklist → typed units (dev-graph nodes, `SCHEMA.md` vocabulary) | Calculate |
| **Group** | typed units + dependency edges → Tier 2 bundles (related items grouped per the partitioning rule; singletons eligible for Tier 3 stay ungrouped) | Calculate |
| **Assign** | Tier 3 ← single checks; Tier 2 ← groups; Tier 1 ← the complete kit (objective + full checklist + specs + Tier 2 results) | Route |
| **Schedule** | assigned units + dependencies + capacity/quotas → dispatch order (dev-graph `cmd_ready` + `govern()` + `route()` + quota reservations) | Route / Calculate |
| **Record** | outputs / results / failures / receipts → Ledger (envelopes `claimed` at dispatch, `established` at check-op PASS) | Track |
| **Repeat** | fixed retry rules → requeue at Allocator tail or dead-letter | Track / Stop |

These ops replace the earlier "Tier 1 → Tier 2 → final glue → merge" language everywhere
in this spec: there is no "final glue" layer and no merge-authority tier — glue work is a
Tier 2 group (or a Tier 1 cross-group concern), and merge is a Compare-against-policy
check op (compatible + authorized only).

## 4. Data flow, stage by stage (overlap points)

1. **Authoring → gate:** human/authoring LLM writes Prompts and the typed work order;
   `admit_action()` compares scope against `dispatch-policy.json` live (never cached).
2. **Gate → partition:** ALLOW receipt (PL-claimed) releases the work order to the Partitioner,
   which emits typed units + `enables` edges into a run-scoped dev-graph.
3. **Partition → allocator (overlap):** `cmd_ready` is recomputed on every acceptance; units whose
   predecessors complete become dispatchable while unrelated units keep running — no barrier.
4. **Allocator → workers (overlap):** quota reservations are per-tick; multiple workers execute
   concurrently within the measured ceilings. Over-ceiling calls are refused by the bucket and
   recorded as `rate_limited` executions (never dispatched).
5. **Workers → ledger (overlap):** every execution writes its `ExecutionResult` receipt to the
   Ledger immediately; the check ops consume receipts as they land (streaming), not at tier end.
6. **Check ops → retry (the repeat):** fixed rules map the 8-class failure taxonomy to
   bounded attempts + backoff + terminal states. Retries re-enter at the Allocator tail —
   dependency-blocked units stay blocked. The queue never stalls on one failure.
7. **Kill-switch (Stop):** `dispatch` kill + `liteboxd /v1/kill` + quota reservation release;
   running requests stop, partial artifacts stay receipted in the Ledger, completed side
   effects are recorded (not rolled back — append-only).

Nothing is timer-driven. All stage transitions are event-driven on completion/receipt/deny
events (AGENTS.md: event-chained waves, no polling crons).

## 5. What the loop does NOT contain

- No LLM judge of objectives, outputs, or other LLMs. A bad objective faithfully executed is a
  human/work-order problem.
- No validator hierarchy: `independent_verifier` and `pl_canon_verifier` are deterministic check
  ops (suite re-runs, envelope verification, chain audits, probe replays) — predicates with
  fixed verdict rules, not judges.
- No autonomous objective reinterpretation: the Typed work order is immutable once authored;
  the Partitioner's rules are explicit; the Allocator's policy is measured limits + bands.
- Cap'n Maps: NOT PRESENT in evidence (f6 §8) — classified BLOCKED/UNKNOWN, assigned NO role
  in this loop (see 01 §C3).
